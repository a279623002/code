# 一、看门狗 Watch‑Dog 完整原理 & 续期策略
## 1.什么是看门狗锁
看门狗并不是 Redis 自带功能，**是客户端侧实现的自动续期机制**，最出名实现：Java‑Redisson。

### 问题背景（为什么需要看门狗）
普通分布式锁流程：
1. `SET lock uuid  EX 10s NX`，锁过期时间 10s
2. 业务开始执行
3. **业务耗时 > 10s**
👉 Redis 锁自动过期，别的进程抢到同一把锁 → **并发安全事故**

看门狗就是解决：**业务没跑完，锁不能过期**。

## 2.核心原理
1. 客户端拿到锁以后，启动一个**后台守护协程**
2. 定时检查，刷新锁的过期时间
3. 业务完成，主动释放锁 → **停止看门狗协程**，锁不再续期
4. 如果进程宕机：看门狗协程死亡，没人续期 → 锁到期自动释放，避免死锁

> ⚠️ 看门狗**只在客户端**，Redis 本身完全不知道看门狗存在。

## 3.标准续期策略（Redisson原版策略）
- 默认锁TTL：`30s`
- **续期间隔 = TTL / 2** → 15s 续一次
- 每次续期：重置过期时间回到初始值（30s）
- 续期Lua脚本必须校验锁的value是否等于当前客户端标识：
```lua
-- 原子续期脚本
if redis.call('GET',KEYS[1]) == ARGV[1] then
    return redis.call('EXPIRE',KEYS[1],ARGV[2])
else
    return 0 -- 锁已经不属于我，停止看门狗
end
```
返回 0 = 锁丢失 → **看门狗协程立刻退出，不再续期**。

### 看门狗完整生命周期
```
客户端获取锁成功
    ↓
启动看门狗协程
    ↓
每隔 TTL/2 执行一次续期Lua脚本
    ↓
┌───────────────┬────────────────┐
│脚本返回1(成功) │脚本返回0(锁丢了)│
└───────────────┴────────────────┘
       ↓                  ↓
继续循环续期        看门狗退出，不再续期
    ↓
业务完成 → UnLock() → cancel停止看门狗协程 → 删除key
```

## 4.续期策略可选方案对比
|策略|触发时机|优缺点|
|---|---|---|
|固定半周期续期(推荐Redisson方案)|TTL/2|延迟平滑，最稳定；生产首选|
|动态剩余时间续期|剩余过期时间 < TTL/3|续期频率更高，开销略大|
|无限递归续期(危险)|每次到期前刷新|如果看门狗卡死，锁永久不死锁，严禁使用|

## 5.看门狗锁 CAP属性
> **单Redis +看门狗锁 ≠ CP锁**
Redis主从是异步复制：
1. 主节点写入锁成功，从节点还没同步锁数据
2. 主宕机，从晋升为主
👉 **锁丢失，多个客户端拿到锁**
所以：**单Redis锁（看门狗）本质 AP，只能做防重，不能做资金强一致扣减**

# 二、Redlock（红锁）完整原理 Redis‑官方算法
## 1.诞生背景
解决单Redis主从切换锁丢失问题。
**前提硬性要求：N台完全独立、无主从、无集群的Redis实例，官方推荐N=5台**

## 2.Redlock 完整算法步骤
> 假设锁TTL = 10s
1. **记录开始时间 startTime = now()**
2. 客户端并行/串行向全部5台独立Redis节点执行加锁：
    `SET lock_key random_uuid EX 10 NX`
3. 统计加锁成功节点数量 successCount
4. **计算加锁耗时 elapsed = now()‑startTime**
5. 锁剩余有效时间 effectiveTTL = TTL - elapsed
6. 判断是否拿到锁：
    - successCount >= Quorum（过半，5节点则≥3）
    - effectiveTTL > 0
👉 两个条件同时成立才算获取锁成功
7. **失败兜底：向所有节点释放锁**，不管有没有加上
8. 执行业务逻辑
9. 完成后：**全部节点执行释放锁(Lua校验uuid)**

释放锁Lua脚本：
```lua
if redis.call('GET',KEYS[1]) == ARGV[1] then
    return redis.call('DEL',KEYS[1])
end
return 0
```

## 3.红锁为什么理论上偏向CP？
过半节点拿到锁。
网络分区出现，分区一侧最多只能拿到2/5节点锁，达不到quorum阈值 → 获取锁失败，宁可失败（牺牲可用性）也不让多客户端拿到锁。

## 4.红锁致命缺陷（Martin Kleppmann争论）
### 坑1：系统时钟漂移（最致命）
Redis依赖机器系统时间做过期。
例子：
5节点，3节点成功拿到锁，TTL=10s。
其中一台Redis机器时钟**回拨**5秒 → 锁提前过期。
这时第二个客户端又拿到3台节点锁 → **双客户端同时持有锁**，一致性破坏。

> 解决办法几乎无解，只能开启Redis延时释放、时钟监控，治标不治本。

### 坑2：进程暂停GC / OS卡顿
客户端GC停顿，停顿期间锁过期，业务还没跑完。

### 坑3：运维成本极高
必须部署**5台完全独立**Redis实例，不能主从、不能集群；资源开销大。

### 坑4：性能差
要和N个Redis节点交互，延迟翻倍。

# 三、看门狗锁 VS Redlock原理对比
|对比项|单Redis+看门狗锁|Redlock红锁|
|---|---|---|
|节点数量|1个Redis|≥5独立Redis实例|
|续期能力|✅ 客户端看门狗自动续期|❌ **原版Redlock没有看门狗！**|
|Quorum过半机制|无|✅ 需要过半成功|
|锁过期控制|客户端定时刷新TTL|锁TTL固定，拿到锁之后不会自动续期|
|时钟依赖|低，续期由客户端控制|高！每个Redis节点系统时钟必须稳定|
|CAP倾向|AP（主从异步可能丢锁）|理论目标CP，但是时钟问题破坏一致性|
|宕机风险|主从切换锁丢失|单节点宕机不影响，过半存活即可|
|生产适用场景|非资金场景：防重复提交、任务幂等|极少推荐，争议大，一般不用|

> 重点提醒：**原生Redlock规范没有看门狗！**
如果你业务耗时很长，自己在红锁上面再加一层客户端看门狗续期，就变成「红锁+看门狗」组合方案，但**时钟漂移风险依然存在**。

# 四、三种分布式锁选型决策树（Go微服务）
1. 普通业务，允许极小概率锁丢失 → **单Redis + 看门狗锁（AP）**
2. 资金、库存强一致，不能超卖 → **etcd分布式锁（原生CP）优先**
3. 不推荐生产用Redlock，除非你充分理解时钟漂移风险。
