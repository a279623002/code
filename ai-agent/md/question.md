## 3. 项目深挖：边端智能助手（RAG）

### 3.1 请介绍这个项目

> 背景：部署在边端盒子上的智能助手，离线/内网环境，给用户做知识库问答。
> 链路：多格式文档 → MarkItDown 统一转 Markdown → 结构感知分块 → bge-large-zh-v1.5 向量化 → FAISS 建索引 → 检索召回 → 拼 Prompt → LLM 生成答案。
> 我负责：文档解析、分块策略、向量检索与混合检索。
> 结果：支持 PDF/Word/Excel/PPT/图片/音频/文本，问答能定位到原文片段。

### 3.2 为什么要先把文档转成 Markdown（由浅入深）

- 浅：多格式统一成一种中间表示，后续分块/清洗只写一套逻辑。
- 深：Markdown 保留了标题层级、列表、表格这些**结构语义**，比纯文本更能表达「这段话属于哪一节」，分块时可以按标题边界切，语义更完整。
- 补充：MarkItDown 对 PDF/Office 支持好，图片走 OCR、音频走 ASR 后再落到文本。

### 3.3 分块策略怎么设计的？为什么不固定长度切？

**固定长度的问题**：会把一句话、一个表格、一个标题和它的正文切断，检索出来的片段语义残缺，召回后 LLM 也答不准。

**我的做法（结构感知分块）**

1. 按 Markdown 标题层级（#/##/###）优先切分，形成「章节块」；
2. 章节块超过阈值（如 500~800 token）时，按段落/列表项二次切分；
3. 相邻小块做**重叠（overlap）**，避免边界信息丢失；
4. 每个块带上**标题路径**（如「第三章 > 3.2 安装步骤」）作为元数据，检索时一起拼进上下文；
5. 表格、代码块不切分，整体作为一个块。

**权衡**：块太小召回准但上下文不足；太大上下文完整但噪声多、embedding 被稀释。所以按结构切 + 控制长度 + 保留标题路径。

### 3.4 FAISS 是什么？为什么选它而不是 Milvus / ES？

> FAISS 是 Facebook 开源的向量检索库，只做「索引 + 近邻搜索」，不带服务化、不带元数据存储。
> 选它的原因：**边端部署**，资源有限，要轻量、可嵌入进程内、无额外服务依赖；数据量在十万级以内，单机够用。
> 对比：Milvus 功能全但要部署集群，重；ES 支持全文+向量但资源占用高。如果数据上百万或要多租户，我会换 Milvus/pgvector。

### 3.5 FAISS 用了哪种索引？原理是什么？

- 小数据量：`IndexFlatIP`（内积）或 `IndexFlatL2`（欧氏距离），**精确检索**，暴力遍历，召回 100% 但 O(N)。
- 大数据量：`IVF`（倒排聚类，先找簇再簇内搜，牺牲少量召回换速度）、`HNSW`（图索引，查询快、内存高）、`PQ`（乘积量化压缩内存）。
- 关键点：**向量先 L2 归一化，内积就等于余弦相似度**，所以我用 Inner Product 表示余弦。

### 3.6 bge-large-zh-v1.5 有什么特点？为什么用它？

> 中文语义 embedding 模型，1024 维，中文检索效果在开源里靠前，可离线部署（边端不能调外部 API）。
> 使用细节：query 侧要加官方指令前缀（"为这个句子生成表示以用于检索相关文章："），doc 侧不加；必须**同一个模型**做入库和查询，否则向量空间不一致。

### 3.7 你说的「混合检索」具体怎么做？

> 向量检索擅长语义相近，但对**专有名词、编号、精确关键词**弱；BM25/关键词检索正好相反。所以两路召回再融合：
> 1. 向量 Top-K + BM25 Top-K 分别召回；
> 2. 用 **RRF（倒数排名融合）** 合并：score = Σ 1/(k + rank)，不需要两路分数归一化；
> 3. 可选加 **Rerank 模型**（cross-encoder）对 Top-N 精排，取 Top-3~5 进 Prompt。
> 效果：专有名词类问题的召回明显改善。

### 3.8 怎么评估检索效果好坏？

> 建一个几十~上百条的评测集（问题 + 标准答案/标准片段），看 **Recall@K、MRR、Top-3 命中率**，再人工看答案准确性。分块策略、embedding 模型、是否 rerank 都做 A/B 对比。

### 3.9 RAG 常见的幻觉怎么治理？

- 检索侧：提高召回质量（分块、混合检索、rerank）、设相似度阈值，低于阈值直接「知识库中没有相关内容」；
- 生成侧：Prompt 强约束「只能基于给定资料回答，并标注引用片段」，temperature 调低；
- 工程侧：答案附带原文出处，便于人工校验；对高频问题做缓存和人工审核。

### 3.10 边端部署有哪些约束？怎么优化

> 约束：CPU/内存/显存有限、可能无外网、模型要本地化。
> 优化：embedding 用 ONNX/量化版本；FAISS 索引用 IVF/HNSW 控制内存；解析和向量化做成异步任务队列；索引持久化到本地磁盘，启动加载；LLM 可接本地小模型或按配置切云端。

### 3.11 文档解析的异常怎么处理（扫描件、加密 PDF、超大文件）

> 扫描件 PDF 没有文本层 → 走 OCR；加密文件先尝试空密码/提示用户；超大文件走异步任务 + 分片处理 + 进度上报；解析失败记录原因并允许用户重试，单文件失败不影响整批导入。

## 4. 项目深挖：算力调度系统

### 4.1 项目介绍

> 基于 Gin 的算力调度系统，管理算力中心/集群/节点三级资源，负责任务的申请、调度、执行、监控和释放。
> 我负责：资源模型设计、Prometheus 指标同步、Grafana 面板、编排策略、K8s 任务下发与状态跟踪、任务日志与报告。

### 4.2 资源模型怎么设计的（三级结构）

> 算力中心（机房/区域）→ 算力集群（K8s 集群）→ 算力节点（机器）。
> 节点维度记录：IP、卡类型（如 A100/昇腾）、卡数、显存、CPU/内存、功耗、健康状态。
> 任务维度记录：任务类型（训练/推理）、所需卡型与卡数、优先级、镜像、超时、状态机。
> 关系：任务申请资源 → 调度器按策略匹配到节点 → 生成 K8s 资源对象 → 回写任务状态。

### 4.3 为什么要从 Prometheus 同步资源，而不是自己上报？

> 节点和 GPU 指标（利用率、显存、功耗、温度）本来就有 node-exporter / DCGM exporter 在采，Prometheus 是统一数据源，直接拉取避免重复造轮子和数据不一致。
> 做法：定时调用 Prometheus HTTP API（instant query）按 label 聚合，落库做资源快照；页面展示和调度决策都基于快照 + 实时查询结合。

### 4.4 调度策略怎么设计的？

> 先过滤后打分：
> 1. **过滤**：卡型匹配、卡数足够、节点健康、资源余量满足、亲和性（指定集群/机房）；
> 2. **打分**：按任务类型加权，比如推理任务偏向低负载节点（打散），训练任务偏向整机空闲节点（聚合，减少碎片）；再叠加优先级、队列公平性；
> 3. **落库 + 下发**：选中的节点生成调度记录，通过 K8s 创建 Job/Deployment。
> 本质上是借鉴 K8s 的 predicates + priorities 思路，在业务层做一层针对 GPU 的编排。

### 4.5 怎么和 K8s 交互？client-go 的 List-Watch 了解吗？

> 用 client-go 的 clientset 创建/查询/删除 Job、Deployment、Pod，读取事件和状态。
> List-Watch：先 List 拿全量，再 Watch 增量事件；client-go 的 **Informer** 在本地维护一份缓存（Store），业务读缓存而不是直连 apiserver，配合 workqueue 做事件处理，避免频繁请求打爆 apiserver。这也是我监控任务状态的主要方式。

### 4.6 任务状态怎么保证最终一致（下发成功但状态丢了怎么办）

> 任务状态机：待调度 → 调度中 → 运行中 → 成功/失败/已终止。
> 一致性手段：
> 1. 以 K8s 为**事实源**，本地状态只是缓存，定时对账（reconcile）修正；
> 2. 状态变更通过 Informer 事件驱动更新，同时落库；
> 3. 幂等：创建时用固定名称/标签（label 带任务 ID），重复下发不会重复建；
> 4. 超时与兜底：调度超时置失败并释放资源，异常退出由定时任务扫描修复。

### 4.7 「推理切流」是怎么做的？

> 新模型版本上线时，先起新版本推理服务，通过 Service/Ingress 权重或网关灰度把一部分流量切过去，观察指标（QPS、延迟、错误率）正常后逐步放大到 100%，异常则回滚到旧版本。核心是**灰度发布 + 可观测 + 可回滚**。

### 4.8 任务日志和工况怎么采集？

> Pod 日志通过 K8s API（logs 接口）流式拉取，或落盘后由 sidecar/采集器上传；工况（GPU 利用率、显存、温度）按任务时间窗从 Prometheus 查询聚合；任务结束后生成报告（汇总指标 + 日志片段）上传对象存储。注意日志要限流和限大小，避免大任务把存储打满。

### 4.9 如果任务一直 Pending 怎么排查

> 1. 看 Pod event：资源不足 / 亲和性不满足 / 镜像拉取失败 / 无可用节点；
> 2. 看节点剩余资源和 taint/toleration；
> 3. 看调度器日志和资源快照是否过期；
> 4. 兜底：Pending 超时告警 + 自动重调度或通知用户。

### 4.10 Prometheus 的指标模型 / PromQL 举几个例子

> 指标模型是「指标名 + label 集合 + 时间戳 + 值」。常用函数：`rate()` 求速率、`sum by()` 聚合、`avg_over_time()`、`histogram_quantile()` 算 P99。
> 例：`sum by (node) (DCGM_FI_DEV_GPU_UTIL)` 看各节点 GPU 利用率；`histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))` 算 P99 延迟。

## 5. 项目深挖：机器人管控平台

### 5.1 项目介绍

> 基于 GoFrame 的机器人管控平台：机器人管理、模型管理、仿真管理。
> 我负责：MQTT 状态订阅、指令下发、模型参数配置、仿真镜像与任务。

### 5.2 为什么用 MQTT 而不是 HTTP / WebSocket

> 机器人在弱网、移动网络下，需要**长连接 + 低开销 + 双向通信**，还要支持一对多下发。MQTT 协议头小、支持 QoS、断线重连和遗嘱消息，天然适合设备接入。HTTP 轮询实时性差、开销大；WebSocket 更偏浏览器场景，设备侧生态不如 MQTT。

### 5.3 主题（Topic）怎么设计

> 按「业务/设备/方向」分层：
> - 状态上报：`robot/{robotId}/status`、`robot/{robotId}/telemetry`（电量、温度）
> - 指令下发：`robot/{robotId}/cmd`
> - 指令回执：`robot/{robotId}/cmd/ack`
> 用通配符 `robot/+/status` 做统一订阅。设计原则：主题层级可枚举、带设备 ID 便于水平扩展和权限隔离。

### 5.4 QoS 0/1/2 的区别，你们用哪个

> 0 最多一次（可能丢）、1 至少一次（可能重复）、2 恰好一次（开销最大）。
> 状态上报用 QoS 0/1（丢了下一周期还有）；指令下发用 QoS 1 + 业务层 ack/去重，保证「至少送达 + 幂等」，不追求协议层恰好一次。

### 5.5 指令下发的可靠性怎么保证

> 1. 每条指令带唯一 commandId，设备回 ack，服务端记录状态；
> 2. 超时未 ack 重试（次数上限 + 退避），避免风暴；
> 3. 设备侧按 commandId 幂等，重复指令不重复执行；
> 4. 离线设备用持久会话/离线消息（cleanSession=false）或等上线后拉取待执行指令；
> 5. 关键指令记录审计日志。

### 5.6 设备离线怎么感知

> 靠 MQTT KeepAlive 心跳 + 遗嘱消息（LWT）：连接断开且超过 1.5 倍心跳周期，broker 判定离线并发布遗嘱到指定 topic，服务端订阅后更新设备状态；同时用「最后上报时间」做兜底判断。

### 5.7 大量设备连接怎么扩展

> Broker 做集群（如 EMQX 集群）、按设备 ID 分片；业务侧无状态水平扩展，订阅端多实例消费；状态落 Redis 做共享；上报数据先入 MQTT 再异步落库，避免直写 DB 打满。

### 5.8 GoFrame 和 Gin 的区别

> Gin 是轻量 HTTP 框架，只做路由和中间件；GoFrame 是**全家桶**：ORM、配置、日志、缓存、校验、定时任务、链路都有，约定大于配置，适合快速做企业级业务系统；代价是框架侵入性强、升级耦合。我在机器人平台用 GoFrame 是为了快速落地 CRUD + 后台管理。

### 5.9 仿真模块怎么做的

> 构建仿真镜像（内置仿真引擎 + 依赖），用户上传自定义脚本，平台把脚本和模型参数挂载到容器里跑仿真任务，输出结果和视频/日志；任务编排复用 K8s/容器，资源隔离靠容器限制。

## 6. 其他项目速答

### 6.1 教务系统：信创数据库适配做了什么

> 达梦、人大金仓都兼容大部分 SQL 标准但方言有差异：分页语法、函数名、`limit/offset`、自增、`group by` 严格模式、时间函数、大小写敏感、驱动。
> 做法：ORM 层统一封装 + 方言适配（GORM 的 dialector / 自定义），SQL 尽量用标准写法，差异点集中到适配层；建表脚本按库分别维护；联调阶段跑全量用例回归。踩坑最多的是分页和隐式类型转换。

### 6.2 教务系统：登录鉴权怎么做的

> 对接统一账号中心做认证，业务侧签发/校验 Token（JWT），网关或中间件统一拦截，解析出用户身份和租户，透传到业务上下文；权限用 RBAC（用户-角色-权限）控制接口和数据范围；Token 短期有效 + Refresh Token 续期，退出登录把 Token 加入 Redis 黑名单。

### 6.3 组织机构模块难点

> 树形结构的增删改查和移动：部门层级、父子关系、负责人、排序；查询要递归（或维护 path/ancestor 字段避免递归）；删除要校验是否有下级/人员；数据权限按组织树做范围过滤。

### 6.4 问卷投票系统：怎么建模多种题型

> 问卷 → 题目 → 选项 → 答卷 → 答案 五张核心表。题目有 type（单选/多选/填空/评分等），答案表用「题目 ID + 值」的通用结构（选项存选项 ID，填空存文本），避免每种题型一张表。统计按题目维度聚合，多选用关联表或 JSON 数组存。

### 6.5 go-zero 的特点

> 微服务框架，内置 API 定义（.api）生成代码、goctl 工具、RPC（zrpc）、熔断限流、链路追踪、缓存管理；适合快速搭微服务。代价是 protobuf/zrpc 生态相对固定，灵活性不如手写。
> 项目里问卷投票系统就是 go-zero：API 层做 HTTP 接入和参数校验，RPC 层拆问卷、题目、答卷几个服务，用 etcd 做注册中心，服务间 zrpc 调用。

**微服务常见追问**

- **服务注册与发现**：go-zero 用 **etcd** 做注册中心。服务启动时把自己 `ip:port` 注册成带 TTL 的 key 并心跳续租，下线时主动删除；调用方通过 `zrpc.MustNewClient(etcd://...)` 订阅，etcd 的 watch 会把实例列表推给客户端，本地维护可用列表。consul、nacos、eureka 思路一致，区别在一致性模型（etcd 是 Raft 强一致，eureka 是 AP）。
- **通信方式**：同步用 **gRPC**（HTTP/2、protobuf、性能好、天然支持流式），go-zero 的 zrpc 就是 gRPC 封装；异步用 MQ 解耦。内部不用 HTTP+JSON，主要是序列化开销和强类型契约。
- **负载均衡**：客户端侧做，拿到实例列表后按 P2C（power of two choices）、轮询或加权选择；go-zero 默认 P2C，比随机更均衡，也不会像轮询那样在慢节点上堆积。
- **熔断**：go-zero 用 **自适应熔断（Google SRE 的 BBR 思路）**，统计成功率和请求量，错误率超阈值自动打开，半开状态放少量请求探测，恢复后关闭。目的是下游挂了别再打过去，避免雪崩。
- **限流**：单机用**令牌桶**（`rate.Limit`）；集群限流需要 Redis 计数或网关统一限流。限流保护自己，熔断保护下游，两者配合。
- **超时与重试**：RPC 必须设超时（`Timeout`），并且**超时要小于上游的超时**，逐层收敛；重试只对幂等接口做，带退避，别在高负载时放大流量。
- **链路追踪**：go-zero 内置 OpenTelemetry / Jaeger 支持，traceId 从网关透传到每个 RPC 和日志，排查问题靠它串链路。
- **配置与网关**：配置走 etcd 或配置文件 + 热更新；统一入口用 API 网关做鉴权、限流、路由、灰度。
- **数据一致性**：拆服务后跨库事务优先用**本地消息表/事务消息 + 补偿**做最终一致，强一致短事务才考虑 TCC/Seata，不轻易上分布式事务。
- **拆分原则**：按业务域（DDD 限界上下文）拆，不按技术层拆；先单体模块化，等团队和流量确实需要再拆，避免「分布式单体」。
- **代价**：调用链变长、排障变难、数据一致性变复杂、运维成本上升，所以小项目不该上微服务。

### 6.6 抽奖：怎么防超卖、怎么保证公平

> Redis Hash 存奖品库存，**Lua 脚本**把「校验资格 + 扣库存 + 记录中奖」做成原子操作，避免并发超卖；概率用区间法（按权重生成区间，随机数落区间）；每人限次用 Set 或计数器；中奖结果异步落库 + 消息队列削峰；接口幂等用唯一键（用户 ID + 活动 ID）。
> 细节：库存预热到 Redis、活动结束对账（Redis 库存与 DB 发放数核对）、限流防刷（IP/用户维度）。

### 6.7 爬虫：RabbitMQ 怎么用的

> Beego 服务 + crontab 定时触发任务，任务投递到 RabbitMQ；用 **direct 交换机**，每种爬虫绑定自己的 routing key 和队列，各消费者独立消费、互不影响，也便于单独扩容和失败重试。失败进死信队列人工/自动重试。去重用 Redis Set / 布隆过滤器，控速用限流 + 代理池。

### 6.8 粤贸：微信扫码登录 / 扫码支付怎么接入（1 分钟速答）

> 登录走微信开放平台的**扫码登录**，本质是 OAuth2 授权码模式：前端跳微信二维码页，用户扫码后微信带 `code` 回调我们后端，后端用 `code + AppID + AppSecret` 换 `openid/unionid` 和用户信息，再查/建本地账号，最后签发我们自己的登录态返回前端。关键点是 `state` 防 CSRF、`AppSecret` 只在服务端、`code` 一次性。
> 支付走 **Native 扫码支付**：服务端调统一下单拿到 `code_url`，前端渲染成二维码；用户付款后微信异步回调 `notify_url`，我们验签、解密、比对金额和订单号，幂等更新订单状态，再返回成功应答；另外用主动查单和定时对账兜底，防止漏单。
> 详细流程和踩坑见 8.9.10、8.10。

### 6.9 爬虫策略与反爬怎么答（1 分钟速答）

> 我是按「调度 → 抓取 → 去重 → 限速 → 解析 → 入库 → 监控」拆的：crontab 定时触发任务投 RabbitMQ，按站点/类型分队列，消费者独立扩容；URL 规范化和 Redis/布隆去重，用时间或 ID 游标做增量；每个域名单独限速、失败指数退避进死信；解析后清洗入库。
> 反爬上主要是维护真实 UA/Header/Cookie、代理池、控制频率避免触发验证码；遇到 JS 签名或动态渲染就走接口或 headless 浏览器；同时遵守 robots 和合规要求，不给对方服务造成压力。
> HTTPS 在 Go 里默认就会校验证书，正常直接请求即可，自签证书才特殊配置，抓包调试走代理；再注意连接复用、超时、重定向和 Cookie 处理。详见 8.14。

## 7. 场景题

### 7.1 线上接口突然变慢，怎么排查（万能模板）

> 1. **看影响面**：哪个接口、错误率、QPS、P99，是否和发布/活动/流量相关；
> 2. **分层定位**：入口（Nginx/网关）→ 服务（CPU/内存/GC/goroutine 数）→ 下游（MySQL 慢查询、Redis 延迟、RPC 超时）→ 外部依赖；
> 3. **看指标和日志**：Prometheus 面板、链路追踪、慢日志、错误日志；
> 4. **常见原因**：慢 SQL/索引失效、缓存击穿、连接池打满、goroutine 泄漏、GC 频繁、下游超时、锁竞争；
> 5. **止血**：限流降级、回滚、扩容、加缓存；**复盘**：加监控告警和压测。

### 7.2 Go 服务内存持续上涨，怎么查

> 1. `pprof` heap 看对象分布（`go tool pprof http://ip/debug/pprof/heap`）；
> 2. 区分「真泄漏」还是「GC 未及时回收」：看 `runtime.MemStats` 的 HeapInuse/HeapObjects 是否单调上涨；
> 3. 常见泄漏：goroutine 泄漏（channel 阻塞、context 未取消）、全局 map 只增不减、未关闭的 response body / 连接、大 slice 引用小 slice 导致底层数组不释放；
> 4. 手段：`pprof` goroutine 看堆积栈、`trace` 看调度、设置 `GOMEMLIMIT` 兜底。

### 7.3 goroutine 数量暴涨 / 泄漏

> 查 `runtime.NumGoroutine()` 和 pprof goroutine 栈；常见原因是 channel 无缓冲且无人消费、select 缺少 default/超时、context 没传递、for 循环里起 goroutine 没退出条件。修复：统一用 `context.WithTimeout` 控制生命周期，channel 要有关闭方，用 errgroup 收敛。

### 7.4 接口 QPS 从 1k 涨到 10k，怎么扛

> 1. 无状态化 + 水平扩容；
> 2. 加缓存（热点数据 Redis，本地缓存做多级）；
> 3. 异步化（写操作走 MQ 削峰）；
> 4. 数据库：读写分离、索引优化、连接池调优、分库分表；
> 5. 限流降级熔断，保护下游；
> 6. 压测验证瓶颈（先用 pprof 和压测找瓶颈，别盲扩）。

### 7.5 如何设计一个秒杀系统

> 前端：按钮防重复、静态资源 CDN。
> 接入层：Nginx 限流、IP/用户维度防刷。
> 服务层：库存预热到 Redis，Lua 原子扣减；资格校验（限购、时间）；成功后发 MQ 异步下单，削峰。
> 数据层：DB 扣减做最终一致 + 唯一索引防重复；订单表按用户/活动分片。
> 兜底：超卖对账、库存回滚、失败重试、限流降级。

### 7.6 如何保证接口幂等

> 方案：唯一业务键（订单号/requestId）+ 唯一索引；Redis `SET NX` 做请求去重（带过期）；状态机校验（已支付不能再支付）；MQ 消费端用去重表或幂等键。关键是「先判重再执行」且判重与执行尽量原子。

### 7.7 分布式锁怎么做（Redis / etcd）

> Redis：`SET key val NX PX 30000` 加锁，value 用唯一标识，释放用 Lua 校验 value 再删；续期用看门狗；集群下 Redlock 有争议，强一致场景用 etcd/ZooKeeper（临时顺序节点）。
> 业务上还要考虑：锁超时与业务耗时、可重入、锁粒度、失败重试。

**看门狗（watchdog）续期原理**

> 问题：锁设了 30s 过期，但业务可能跑 60s，锁提前释放会导致并发写。
> 做法（Redisson 模型）：
> 1. 加锁成功后，注册一个**后台定时任务**，按 `过期时间 / 3`（30s 锁就是每 10s）检查一次；
> 2. 检查这个锁是否还**属于当前线程**（value 比对），是就执行 `PEXPIRE` 把过期时间重置回 30s；
> 3. 释放锁时取消定时任务，避免无意义续期；
> 4. Java 里靠 `ThreadLocal` 记录「当前线程持有的锁」，所以锁能被同一线程重入；Go 里没有线程本地存储，通常把锁句柄和 `context`/goroutine 绑定，或者在加锁时返回一个 `Lock` 对象持有续期 `cancel`。
> 关键点：
> - 续期必须**校验持有者**，否则会帮别人续锁；
> - 定时任务在进程内，**进程被 kill 就停止续期**，锁会在一个 TTL 后自动释放，不会永久死锁；
> - 网络分区时可能出现「以为续上了但服务端没成功」，所以业务仍需幂等或版本号兜底；
> - 续期只是延长 TTL，不是无限；业务真可能跑很久，应改用「任务租约 + 幂等」而不是死等锁。
> etcd/ZooKeeper 的租约是同一思路：客户端定期续租（KeepAlive），会话断开就自动删节点释放锁。

### 7.8 缓存和数据库一致性怎么保证

> 常用 **Cache Aside**：读时缓存未命中查库回填；写时**先更新库、再删缓存**，并给缓存设过期时间兜底。延迟双删应对并发读写；强一致场景用 binlog 订阅（Canal）异步删缓存。极端不一致可接受「最终一致」，关键交易走库。

### 7.9 消息重复消费 / 消息丢失怎么处理

> 重复：消费端幂等（唯一键 + 去重表 / 状态机）。
> 丢失：生产端 confirm + 持久化，消费端手动 ack（处理成功才 ack），队列/交换机持久化，broker 做镜像/集群；消费失败进死信队列重试 + 告警。

### 7.10 线上出现死锁 / 数据库连接池耗尽

> 死锁：`show engine innodb status` 看最近死锁；业务上统一加锁顺序、缩短事务、避免大事务；捕获死锁异常重试。
> 连接池耗尽：看 `max_open_conns`、慢 SQL 是否长时间占用、是否有事务未提交/连接未释放；先扩容连接池 + 杀慢查询止血，再优化 SQL。

### 7.11 需要保证任务「至少执行一次」且不重复执行

> 任务表 + 状态机 + 乐观锁（version 或 `update ... where status = 'pending'`），抢到锁的实例执行；执行中加租约/超时，避免实例挂掉任务卡死；执行完写幂等结果表；定时扫描超时任务重投。

### 7.12 跨服务数据一致性（下单扣库存 + 扣款）

> 优先避免分布式事务：用**本地消息表 / 事务消息 + 补偿**实现最终一致（先落本地事务和消息，再异步通知下游，失败重试 + 对账）；强一致且短事务可用 TCC；简单场景用 Saga 编排 + 补偿接口。

### 7.13 灰度发布怎么做

> 按流量比例/用户白名单/请求头路由到新版本；新版本先小流量，观察错误率、延迟、业务指标；异常一键回滚（保留旧版本）；K8s 侧可用 Deployment 双版本 + Service 权重 / Ingress 灰度 / 服务网格。

### 7.14 如何在 K8s 里发布不中断服务

> 滚动更新 + `maxSurge/maxUnavailable`；配置 readinessProbe，就绪后才接流量；优雅停机（preStop + 处理 SIGTERM，先摘流量再退出，等待在途请求完成）；资源 requests/limits 合理，避免 OOM 和调度失败。

### 7.15 只给你一个日志文件，怎么快速定位问题

> 先 grep 错误关键字和 traceId，按时间窗口收敛；看请求入口和出口日志之间耗时；统计错误码分布找共性；结合上下游调用日志串链路。平时就要保证日志有 traceId 和结构化字段。

### 7.16 让你从零设计一个 RAG 知识库平台，怎么设计

> 接入层：文档上传（多格式）、解析任务队列；处理层：解析 → 清洗 → 分块 → embedding → 建索引（版本化）；检索层：向量 + 关键词混合召回 + rerank；生成层：Prompt 模板 + LLM + 引用；管理层：知识库/文档/权限/评估集；运维：任务监控、失败重试、索引重建、效果评估。

## 8. 常见八股文

### 8.1 Go 语言

#### 8.1.1 GMP 调度模型

> G（goroutine，用户态协程）、M（内核线程）、P（逻辑处理器，数量 = GOMAXPROCS）。
> 调度：P 持有本地运行队列，M 绑定 P 执行 G；本地队列空了从全局队列或其他 P **偷取（work stealing）**；G 阻塞系统调用时 M 与 P 解绑（hand off），P 找新 M 继续跑，避免浪费。
> 优点：用户态调度开销小，能轻松支撑几十万 goroutine。

#### 8.1.2 goroutine 和线程的区别

> goroutine 初始栈 2KB 可动态扩缩、用户态调度、创建销毁成本低；线程栈 MB 级、内核调度、切换要陷入内核。goroutine 之间用 channel 通信，符合 CSP。

#### 8.1.3 channel 的底层结构

> 环形缓冲区（buf）+ 发送队列 sendq + 接收队列 recvq，等待的 goroutine 封装成 sudog + 互斥锁（mutex）保护。
> 规则：无缓冲 channel 必须收发配对；向已关闭 channel 发送会 panic，接收返回零值；关闭后 range 会退出。channel 是并发安全的，但**不是**用来替代锁做所有同步。

#### 8.1.4 channel 和 mutex 怎么选

> 数据传递、解耦、控制并发用 channel；单纯保护共享状态用 mutex（更轻、语义直接）。不要用 channel 模拟锁。

#### 8.1.5 Go GC 原理

> 三色标记 + 并发标记清除（1.5 起并发，1.8 起**混合写屏障**解决并发标记的对象丢失）。
> 流程：STW 准备 → 并发标记 → STW 标记终止 → 并发清理。
> 调优：`GOGC`（默认 100，堆翻倍触发）、`GOMEMLIMIT`（1.19+ 软内存上限）、减少对象分配（对象复用、sync.Pool）。

#### 8.1.6 三色标记为什么需要写屏障

> 并发标记时用户程序还在改指针，可能出现「黑色对象引用白色对象且灰色对象不再可达」导致对象被误删。写屏障在指针写入时做记录（混合写屏障同时保证强三色不变式和弱三色不变式），保证不丢对象。

#### 8.1.7 内存逃逸

> 编译器判断变量是否「逃出函数作用域」：返回指针、被闭包捕获、大小不定、interface 装箱等会分配到堆；否则分配在栈，函数返回自动回收。
> 查看：`go build -gcflags="-m"`。优化：减少指针返回、避免不必要的 interface、预分配容量。

#### 8.1.8 slice 底层与扩容

> 结构：指向底层数组的指针 + len + cap。
> 扩容：容量小于 256 时约翻倍；大于等于 256 时按 1.25 倍增长并做内存对齐。扩容会**拷贝**，大 slice 频繁 append 要预分配 `make([]T, 0, n)`。
> 坑：`append` 后新 slice 可能与原 slice 共享底层数组；切片截取不会释放底层数组内存。

#### 8.1.9 map 底层与并发问题

> 哈希表 + 桶（每桶 8 个 key），负载因子超过 6.5 触发**增量扩容**（翻倍），过多溢出桶触发**等量扩容**。
> map 非并发安全，并发读写会 fatal；用 `sync.RWMutex` 或 `sync.Map`（读多写少、key 稳定的场景更合适）。

#### 8.1.10 defer 的执行顺序和原理

> 后进先出（LIFO），在函数返回时执行；1.14 起有 open-coded defer 优化，常规场景几乎零开销。注意：defer 的参数在声明时求值；`recover` 只有在 defer 中调用才有效。

#### 8.1.11 panic / recover

> panic 触发后按调用栈执行 defer，遇到 recover 则恢复执行；recover 只在 defer 内直接调用有效。服务里通常在中间件统一 recover，记录堆栈并返回 500，避免进程退出。

#### 8.1.12 interface 底层

> 空接口 `eface`（type + data），带方法接口 `iface`（itab + data）；itab 缓存类型到方法表的映射。nil interface 与「持有 nil 指针的 interface」不相等，是常见坑。

#### 8.1.13 context 的作用

> 用于跨 goroutine 传递取消信号、超时和少量元数据。`WithCancel/WithTimeout/WithValue`，通过 Done() 通道感知取消。规范：作为函数第一个参数，不存结构体，Value 只放请求级元数据（traceId、用户身份）。

#### 8.1.14 sync.WaitGroup / Once / Pool

> WaitGroup 计数等待，Add 要在起 goroutine 前调用；Once 保证只执行一次（如单例初始化）；Pool 复用临时对象降低 GC 压力（如 buffer），但不保证一定命中。

#### 8.1.15 Go 的锁：Mutex 正常模式与饥饿模式

> 正常模式：等待者排队但允许新来的 goroutine 抢锁（自旋），吞吐高但可能饥饿；等待超过 1ms 切换到饥饿模式，锁直接交给队首，保证公平。1.9 起引入饥饿模式。

#### 8.1.16 如何优雅关闭服务

> 监听 SIGTERM/SIGINT → 停止接收新请求（`http.Server.Shutdown(ctx)`）→ 等待在途请求完成 → 关闭连接池/MQ/定时任务 → 退出。配合 K8s preStop 和优雅停机时间。

#### 8.1.17 常见性能优化手段（Go）

> 减少内存分配（预分配、对象池）、避免频繁加锁（分片锁/原子操作）、批量处理、连接池复用、pprof 定位（CPU/内存/阻塞/goroutine）、避免大 JSON 反复序列化、用 `sync.Pool` 复用 buffer。

### 8.2 MySQL

#### 8.2.1 索引为什么用 B+ 树

> 相比 B 树：非叶子节点不存数据，同样页大小能存更多键，树更矮（3 层可存千万级）；叶子节点用链表相连，范围查询和排序友好；相比哈希：支持范围查询和排序；相比二叉树：层数低，磁盘 IO 少。

#### 8.2.2 聚簇索引和二级索引

> InnoDB 主键是聚簇索引，叶子节点存整行数据；二级索引叶子存主键值，查询非索引列需要**回表**。用覆盖索引可避免回表。

#### 8.2.3 最左前缀原则 / 索引失效场景

> 联合索引 (a,b,c) 按 a、a+b、a+b+c 生效。
> 失效：对索引列做函数/运算、隐式类型转换（字符串列传数字）、以 % 开头的 like、or 中有非索引列、不满足最左前缀、优化器判断走索引更贵（区分度低）。

#### 8.2.4 事务隔离级别

> 读未提交、读已提交（RC）、可重复读（RR，InnoDB 默认）、串行化。
> RC 解决脏读；RR 通过 MVCC 解决不可重复读，通过 next-key lock 解决幻读（大部分场景）。

#### 8.2.5 MVCC 原理

> 每行有隐藏字段：事务 ID、回滚指针；undo log 形成版本链；ReadView 记录活跃事务集合，按可见性规则沿版本链找到可见版本。RR 在事务第一次快照时创建 ReadView（全程复用），RC 每次查询都新建。

#### 8.2.6 InnoDB 的锁

> 按粒度：表锁、行锁；行锁分记录锁、间隙锁、临键锁（记录+间隙，RR 下防幻读）、插入意向锁。加锁取决于索引命中情况——**没走索引会退化成锁全表/大量行**。死锁靠等待图检测，回滚代价小的事务。

#### 8.2.7 慢查询怎么优化

> 1. 开慢日志定位 SQL；2. `explain` 看 type（避免 ALL）、key、rows、Extra（Using filesort / temporary 要优化）；3. 加合适索引、改写 SQL（避免 select *、分页深翻用游标/延迟关联）；4. 减少回表、拆分大查询、读写分离、必要时归档/分表。

#### 8.2.8 分库分表

> 垂直：按业务拆库、按字段拆表；水平：按分片键（用户 ID/订单 ID）取模或范围。
> 问题：跨分片查询和聚合、分布式事务、全局 ID（雪花算法/号段）、扩容迁移（双写 + 数据校验 + 切流）。

#### 8.2.9 主从复制与延迟

> 原理：主库写 binlog → 从库 IO 线程拉取写 relay log → SQL 线程回放。
> 延迟原因：大事务、从库单线程回放（可开并行复制）、从库压力大。解决：读写分离时强一致读走主库、半同步复制、监控 Seconds_Behind_Master。

#### 8.2.10 深分页为什么慢，怎么优化

> `limit 1000000, 20` 要扫描并丢弃前 100 万行。优化：用主键游标 `where id > last_id order by id limit 20`；或延迟关联先查主键再回表。

### 8.3 Redis

#### 8.3.1 常用数据结构与底层

> String（SDS）、Hash（listpack/哈希表）、List（quicklist）、Set（intset/哈希表）、ZSet（listpack + 跳表）。跳表支持范围查询，实现比平衡树简单。

#### 8.3.2 为什么 Redis 快

> 纯内存、单线程避免锁竞争和上下文切换、IO 多路复用（epoll）、高效数据结构。6.0 起网络 IO 多线程，命令执行仍是单线程。

#### 8.3.3 持久化 RDB 和 AOF

> RDB：快照，体积小、恢复快，但可能丢数据；AOF：追加写命令，实时性好，可重写压缩；4.0 起支持混合持久化（RDB 全量 + AOF 增量），兼顾恢复速度和数据安全。

#### 8.3.4 过期删除与内存淘汰

> 过期删除：惰性删除（访问时判断）+ 定期删除（抽样）。
> 淘汰策略 8 种：noeviction、volatile/allkeys 下的 lru、lfu、random、ttl。缓存场景常用 allkeys-lru 或 allkeys-lfu。

#### 8.3.5 缓存穿透 / 击穿 / 雪崩

> 穿透：查不存在的数据 → 缓存空值 + 布隆过滤器。
> 击穿：热点 key 过期瞬间大量请求打库 → 互斥锁重建 / 逻辑过期 / 热点永不过期。
> 雪崩：大量 key 同时过期或 Redis 挂 → 过期时间加随机、多级缓存、集群高可用、熔断降级。

#### 8.3.6 分布式锁的实现要点

> `SET key uniqueVal NX PX ttl`；释放时 Lua 比对 value 再删（防误删）；业务超时用看门狗续期；集群场景可用 Redlock（有争议）或直接上 etcd/ZooKeeper。

#### 8.3.7 大 key / 热 key

> 大 key：value 过大或元素过多，导致阻塞、网络拥塞、删除卡顿 → 拆分、压缩、异步删除（UNLINK）。
> 热 key：单 key 高并发 → 本地缓存、key 打散（加随机后缀分片）、读写分离/多副本。

#### 8.3.8 Redis 集群

> 主从 + 哨兵：哨兵做故障检测和主从切换；Cluster：16384 个槽位分片，客户端按 key 路由，支持水平扩展，多 key 操作需在同一槽（hash tag）。

#### 8.3.9 为什么用 Lua 脚本

> Redis 执行 Lua 是**原子**的（单线程执行整段脚本），适合「判断 + 扣减 + 记录」这类需要原子性的组合操作（库存扣减、限流、分布式锁释放）。注意脚本要短，避免长时间阻塞。

### 8.4 消息队列

#### 8.4.1 为什么用 MQ

> 解耦、异步、削峰。代价是复杂度：消息可靠性、重复消费、顺序性、积压、事务一致性。

#### 8.4.2 RabbitMQ 的交换机类型

> direct（按 routing key 精确匹配）、topic（通配符匹配）、fanout（广播）、headers（按头匹配）。

#### 8.4.3 如何保证消息不丢

> 生产端：publisher confirm / 事务；Broker：交换机、队列、消息持久化；消费端：手动 ack（处理成功再确认）；再加死信队列兜底。

#### 8.4.4 RabbitMQ 和 Kafka 怎么选

> RabbitMQ：延迟低、路由灵活、单条消息可靠性机制完善，适合业务消息；Kafka：高吞吐、分区顺序、可回溯消费，适合日志/大数据/流处理。详细对比见 8.4.18。

#### 8.4.5 消息积压怎么办

> 先定位原因（消费慢/消费者挂/突发流量）；短期扩容消费者（注意分区/队列数量限制）、提高批量消费、降级非核心逻辑；长期优化消费逻辑和限流。

#### 8.4.6 Kafka 的核心概念与架构

> - **Broker**：一个 Kafka 节点（服务实例），多个 Broker 组成集群；
> - **Topic**：逻辑上的消息分类，生产者发到 Topic，消费者订阅 Topic；
> - **Partition**：Topic 的物理分片，每个分区是一个**追加写的日志文件**，**分区内有序、跨分区无序**；
> - **Replica**：分区的副本，分 `leader` 和 `follower`，leader 对外读写，follower 同步数据，leader 挂了从 ISR 里选新 leader；
> - **Offset**：消息在分区内的唯一位置（递增编号），消费者靠它记录消费进度；
> - **Producer / Consumer / Consumer Group**：同组内的消费者分摊分区，一个分区同一时刻只被组内一个消费者消费；
> - **Controller**：负责分区 leader 选举、副本状态等元数据管理（老版本靠 ZooKeeper，新版本用 KRaft）。
> 关键差异：Kafka 的消息**消费后不会删除**，按保留策略（时间/大小）清理，所以可以重置 offset 回溯重放。

#### 8.4.7 Kafka 为什么吞吐高

> 1. **顺序追加写**：日志 append-only，避免磁盘随机写；
> 2. **page cache**：读写走操作系统页缓存，不直接频繁刷盘；
> 3. **零拷贝（sendfile）**：数据从文件直接送到 socket，少两次内存拷贝；
> 4. **批量 + 压缩**：生产端攒批（`batch.size`、`linger.ms`），支持 lz4/zstd/snappy 压缩；
> 5. **分区并行**：一个 Topic 多分区，生产/消费都能水平扩展；
> 6. **稀疏索引**：用 index + timeindex 快速定位 offset，不用全量扫描；
> 7. **拉模式**：消费者按自己的能力 fetch，不会被打爆。

#### 8.4.8 生产端怎么保证可靠（acks / retries / 幂等）

> - `acks=0`：发出去不等确认，最快但可能丢；`acks=1`：leader 落盘即确认；`acks=all`（-1）：ISR 中所有副本都确认，最可靠；
> - 配 `retries` + `retry.backoff.ms` + `delivery.timeout.ms` 控制重试；
> - `enable.idempotence=true`：开启幂等生产者，重试不会产生重复消息（依赖 `acks=all` 和重试配置）；
> - 可靠性组合：`acks=all` + `min.insync.replicas>=2` + `replication.factor=3`，ISR 不足时宁可写失败也不丢数据；
> - 想保证同 key 顺序：用 key 做分区，同一 key 永远落同一分区。
> 注意：幂等生产者只解决「发送重试不重复」，不代表消费端不会重复消费。

#### 8.4.9 消费端怎么保证不丢、不重复

> - 关闭自动提交：`enable.auto.commit=false`，业务处理成功后再 `commitSync/commitAsync`，即 **at-least-once**；
> - 如果先提交 offset 再处理业务，进程挂了就会丢消息；
> - 重复消费无法完全避免（rebalance、提交失败、重试），要靠**业务幂等**：唯一键 + 唯一索引、去重表、状态机；
> - `auto.offset.reset=earliest/latest`：只在没有已提交 offset 或 offset 越界时生效，不是「每次都从头消费」；
> - 想端到端 exactly-once 见 8.4.14。
> 关键参数：`max.poll.records`（单次拉多少）、`max.poll.interval.ms`（两次 poll 的最大间隔，超时会被踢出组触发 rebalance）、`session.timeout.ms`、`heartbeat.interval.ms`。

#### 8.4.10 ISR / HW / LEO 是什么

> - **LEO（Log End Offset）**：分区日志末端下一条消息的 offset；
> - **ISR（In-Sync Replicas）**：和 leader 保持同步的副本集合，follower 落后超过 `replica.lag.time.max.ms` 会被踢出 ISR；
> - **HW（High Watermark）**：ISR 中最小的 LEO，消费者**只能读到 HW 之前的消息**，保证读到的数据所有副本都有；
> - `min.insync.replicas`：ISR 至少保留几个副本，少于阈值时 `acks=all` 的写入直接失败，防止副本不足还继续写；
> - `unclean.leader.election.enable=false`：禁止落后太多的副本当 leader，避免丢数据（可用性换一致性）。
> 一句话：**acks 决定写多可靠，ISR 决定当前有几个副本可信，HW 决定消费者能看到哪。**

#### 8.4.11 分区和副本怎么设计

> - 分区数决定**最大并行度**：消费并发上限约等于分区数（一个分区同时只能被组内一个消费者消费）；
> - 经验值：按目标吞吐 ÷ 单分区吞吐估算，再留余量；单分区几万到十几万 QPS 视消息大小而定；
> - 副本数一般 **3**（能容忍 1 个 broker 挂），配合 `min.insync.replicas=2`；
> - 分区数**只能增不能减**，扩容会改变 key 到分区的映射，破坏既有顺序语义，要提前规划；
> - key 分布不均会导致**分区热点**，可加随机后缀或自定义分区器打散。

#### 8.4.12 怎么保证消息顺序

> Kafka **只保证分区内有序**。
> - 需要同一业务实体有序：用业务 ID 做 key（如订单号），同 key 落同一分区；
> - 需要全局有序：只能单分区，牺牲并行和吞吐；
> - 消费端要保证分区内单线程顺序处理，多线程处理会打乱顺序；
> - 注意 rebalance、多分区、消费端并发都可能导致「看起来乱序」。

#### 8.4.13 Consumer Group 与 Rebalance

> 同组消费者分摊分区，实现「一条消息组内只消费一次」；不同组各自消费全量，实现广播。
> Rebalance 触发：消费者加入/离开、心跳超时、订阅关系变化、分区数变化。
> 影响：重平衡期间消费暂停，offset 提交时机可能导致重复消费。
> 优化：调大 `session.timeout.ms`、合理设置 `max.poll.interval.ms`（别让单批处理太久）、用 **static membership**（`group.instance.id`）避免滚动重启触发重平衡、用 cooperative-sticky 分配器减少停顿。

#### 8.4.14 Kafka 的 Exactly Once 怎么做到

> 1. **幂等生产者**：`enable.idempotence=true`，重试不会重复写入；
> 2. **事务生产者**：`transactional.id`，把「跨分区写 + offset 提交」放进一个事务，保证读-处理-写原子；
> 3. **下游幂等**：sink 端用唯一键/事务表去重。
> Kafka 的 EOS 主要适用于 Kafka Streams / 流处理场景；普通业务消费端更常用「at-least-once + 业务幂等」，成本更低。

#### 8.4.15 消息保留与清理（delete / compact）

> Kafka 不因消费而删除消息，按策略清理：
> - **delete**：按时间（`log.retention.hours`）或大小（`log.retention.bytes`）删除整个 segment；
> - **compact**：按 key 保留最新值，适合 changelog、CDC、状态恢复（注意 tombstone 删除标记）；
> - 还有 `segment.ms/segment.bytes` 控制 segment 滚动。
> 所以 Kafka 可以「回溯重放」，但存储成本要提前规划。

#### 8.4.16 KRaft 和 ZooKeeper

> 老架构用 ZooKeeper 存元数据、做 controller 选举；KRaft 模式把元数据管理内置到 Kafka 的 quorum controller，去掉 ZK 依赖，部署更简单、元数据扩展性更好。2.8 引入，3.x 逐步成熟，新集群建议 KRaft。

#### 8.4.17 消息积压怎么排查处理（Kafka 版）

> 1. 先看 lag：`kafka-consumer-groups.sh --describe --group g`，`LAG = LEO - committed offset`；
> 2. 定位是「消费慢」还是「生产突增」：看消费耗时、下游 DB/RPC、GC、`max.poll.records`；
> 3. 扩容消费者：**不能超过分区数**，多了会空闲；
> 4. 分区不够就加分区（注意 key 顺序影响），或临时把消息转存到新 Topic 用更多分区并行消费；
> 5. 优化消费逻辑：批量写、异步化、跳过非核心逻辑、加缓存；
> 6. 生产侧限流/降级，先止血再根治。

#### 8.4.18 Kafka 和 RabbitMQ 全面对比

| 维度 | Kafka | RabbitMQ |
| --- | --- | --- |
| 定位 | 分布式流平台 / 提交日志 | 消息代理（Broker） |
| 吞吐 | 极高，单集群可达百万级/秒 | 中等，万级~十万级/秒 |
| 延迟 | 毫秒级，批量发送会更高 | 微秒~毫秒，低延迟更好 |
| 消息模型 | 分区日志，消息保留、可回溯 | 队列，消费后删除 |
| 消费方式 | 消费者**拉**，自己维护 offset | Broker **推**，消费者 ack |
| 顺序性 | 分区内有序 | 单队列有序，多消费者竞争即无序 |
| 路由能力 | 弱，只有 topic/partition，靠 key | 强，direct/topic/fanout/headers |
| 回溯重放 | 支持（重置 offset） | 不支持，只能重新投递 |
| 扩展性 | 分区水平扩展，天然分布式 | 镜像/集群，扩展相对有限 |
| 可靠性机制 | 副本 + acks + ISR + HW | 持久化 + publisher confirm + 手动 ack + 死信 |
| 事务 / EOS | 支持事务和 exactly-once | 无 EOS，靠业务幂等 |
| 运维复杂度 | 较重（分区、副本、ISR、磁盘、重平衡） | 相对轻 |
| 典型场景 | 日志、埋点、流处理、大数据、削峰缓冲、CDC | 业务解耦、任务队列、RPC、通知、低延迟消息 |

> 一句话选型：**要吞吐、要回溯、要流式处理选 Kafka；要低延迟、要灵活路由、要单条可靠投递选 RabbitMQ。**

#### 8.4.19 项目里为什么选 RabbitMQ 而不是 Kafka

> 爬虫项目的任务是「定时触发 + 按站点分类下发 + 失败重试」，消息量不大、要求低延迟、路由隔离清晰（direct 交换机按 routing key 分队列）、需要单条 ack 和死信队列，RabbitMQ 更合适，运维也轻。
> 如果换成每天亿级的日志/埋点采集、需要回溯重放、要做实时流计算或 CDC，我会选 Kafka。选型要看场景，不能默认 Kafka 更好。

#### 8.4.20 Kafka 常见线上问题速查

> 1. **Consumer Lag 持续上涨**：消费能力不足、下游慢、分区太少、消费者频繁 rebalance；
> 2. **ISR 缩水 / UnderReplicatedPartitions**：broker 挂了、网络抖动、磁盘慢、follower 同步跟不上；
> 3. **频繁 Rebalance**：心跳超时（GC/网络）、`session.timeout.ms` 太小、单批处理超过 `max.poll.interval.ms`；
> 4. **消息丢失**：`acks=0/1`、`min.insync.replicas` 配置不当、自动提交 offset、unclean leader 选举；
> 5. **重复消费**：at-least-once 本身、rebalance、offset 提交失败、重试 → 业务幂等兜底；
> 6. **消息乱序**：跨分区、key 设计不当、消费端多线程并发处理；
> 7. **磁盘满**：retention 配置过大、segment 太大、流量突增；
> 8. **发送超时**：`acks=all` + ISR 不足、网络或 broker 负载高，先看 broker 指标和 ISR；
> 9. **分区热点**：key 倾斜，加随机后缀或自定义分区器；
> 10. **消费者被踢出组**：处理太慢或心跳配置不合理，先解决阻塞再调参数。

### 8.5 Kubernetes / 云原生

#### 8.5.1 Pod / Deployment / Service 的关系

> Pod 是最小调度单元，共享网络和存储；Deployment 管理 ReplicaSet 和副本数，支持滚动更新和回滚；Service 为一组 Pod 提供稳定访问入口（ClusterIP/NodePort/LoadBalancer），通过 label selector 关联。

#### 8.5.2 探针

> livenessProbe（存活，失败重启）、readinessProbe（就绪，失败摘流量）、startupProbe（启动慢的应用先探测，成功后才启用其他探针）。

#### 8.5.3 资源限制与 QoS

> requests 决定调度（保证资源），limits 限制上限；超过内存 limit 会被 OOMKill，CPU 超限被限流。QoS 分 Guaranteed / Burstable / BestEffort，影响驱逐优先级。

#### 8.5.4 调度影响因素

> 资源余量、nodeSelector、nodeAffinity、podAffinity/antiAffinity、taint/toleration、拓扑分布、优先级与抢占。

#### 8.5.5 HPA 原理

> 根据指标（CPU/内存/自定义指标）计算期望副本数：期望 = 当前副本 × (当前指标 / 目标指标)，周期性调整，配合 metrics-server 或 Prometheus Adapter。

#### 8.5.6 ConfigMap / Secret / PV / PVC

> ConfigMap 存配置、Secret 存敏感信息（base64，非加密，需配合加密存储）；PV 是存储资源，PVC 是申请，StorageClass 支持动态供给。

### 8.6 网络与协议

#### 8.6.1 TCP 三次握手 / 四次挥手

> 握手：SYN → SYN+ACK → ACK，确认双方收发能力并同步序号。挥手：FIN → ACK → FIN → ACK，因为 TCP 全双工，两个方向要分别关闭。

#### 8.6.2 为什么需要 TIME_WAIT，大量 TIME_WAIT 怎么办

> 保证最后一个 ACK 能到达、让旧连接报文在网络中消亡（2MSL）。大量 TIME_WAIT 通常是短连接多：用连接池/长连接、调 `tcp_tw_reuse`、增加本地端口范围。

#### 8.6.3 HTTP/1.1、HTTP/2、HTTP/3

> 1.1：长连接但队头阻塞；2：多路复用、头部压缩、二进制分帧，仍有 TCP 层队头阻塞；3：基于 QUIC/UDP，解决 TCP 队头阻塞，支持连接迁移。

#### 8.6.4 HTTPS 握手过程

> 客户端 ClientHello（支持的套件、随机数）→ 服务端 ServerHello + 证书 → 客户端校验证书、生成预主密钥用公钥加密 → 双方用随机数派生会话密钥 → 对称加密通信。核心是**非对称加密交换密钥，对称加密传输数据**。

#### 8.6.5 gRPC 和 REST 的区别

> gRPC 基于 HTTP/2 + Protobuf，二进制、体积小、性能高、支持流式；REST 基于 HTTP/JSON，通用性好、易调试。内部服务间高频调用适合 gRPC，对外 API 用 REST。

#### 8.6.6 WebSocket / SSE

> WebSocket 全双工，适合双向实时通信；SSE 是服务端单向推送（基于 HTTP），实现简单、自动重连，适合 LLM 流式输出、通知推送。

#### 8.6.7 常见状态码

> 200/201/204、301/302/304、400/401/403/404/405/409/429、500/502/503/504。502 是网关拿到无效响应（后端挂了），504 是网关超时。

### 8.7 系统设计与通用

#### 8.7.1 限流算法

> 计数器（有临界问题）、滑动窗口、漏桶（恒定速率）、令牌桶（允许突发）。分布式限流用 Redis + Lua 或网关层实现。

#### 8.7.2 熔断、降级、隔离

> 熔断：下游错误率超阈值直接快速失败，半开试探恢复；降级：返回兜底数据/关闭非核心功能；隔离：线程池/信号量/连接池隔离，避免一个依赖拖垮整个服务。

#### 8.7.3 分布式 ID

> 雪花算法（时间戳 + 机器 ID + 序列）、号段模式（数据库批量取号）、Redis 自增。要求：全局唯一、趋势递增、高可用。

#### 8.7.4 一致性哈希

> 节点和 key 映射到哈希环，key 顺时针找第一个节点；节点增减只影响相邻区间。用虚拟节点解决数据倾斜。

#### 8.7.5 如何做接口设计（RESTful）

> 资源用名词、动作用 HTTP 方法、状态码语义化、版本化（/v1）、分页/排序/过滤参数统一、错误码统一结构、幂等设计（PUT/DELETE）、鉴权和限流在网关统一做。

### 8.8 AI / RAG 相关（加分项）

#### 8.8.1 RAG 的完整流程

> 离线：解析 → 清洗 → 分块 → embedding → 入向量库。
> 在线：query 改写 → embedding → 向量/混合召回 → rerank → 拼上下文 → LLM 生成 → 返回答案 + 引用。

#### 8.8.2 embedding 和向量检索原理

> embedding 把文本映射到高维向量，语义相近的向量距离近；检索用余弦相似度/内积/欧氏距离找 Top-K。维度越高表达力越强但存储和计算成本更高。

#### 8.8.3 怎么降低大模型成本 / 延迟

> 缓存（问题级和语义级）、小模型处理简单任务、流式输出、控制上下文长度（只传 Top-K 片段）、批量请求、异步化、本地化部署。

#### 8.8.4 LangChain 解决了什么

> 把 LLM 应用常见能力抽象成组件：模型调用、Prompt 模板、文档加载与切分、向量库、Retriever、Tool/Agent、记忆。好处是快速编排和替换组件；代价是抽象层多、调试链路长，简单场景可以直接调 SDK。

## 8.9 认证与授权：OAuth2 / JWT / 微信登录

### 8.9.1 OAuth2 是什么？四个角色分别是谁

> OAuth2 是**授权协议**，解决的问题是「第三方应用如何在用户不暴露密码的前提下，拿到访问用户资源的权限」。
> 四个角色：
> - **Resource Owner**：用户，资源的所有者；
> - **Client**：第三方应用（我们的平台）；
> - **Authorization Server**：授权服务器（微信、GitLab、公司统一账号中心）；
> - **Resource Server**：资源服务器，校验 `access_token` 后返回数据。
> 核心产物是 `access_token`（有时还有 `refresh_token`），它代表「客户端被授权做某事」，而不是「用户是谁」。

### 8.9.2 授权码模式（authorization code）完整流程

> 1. 客户端把用户导向授权端点：`/authorize?response_type=code&client_id=xx&redirect_uri=xx&scope=xx&state=随机值`
> 2. 用户在授权服务器上登录并同意授权；
> 3. 授权服务器 302 回 `redirect_uri?code=CODE&state=STATE`；
> 4. **客户端后端**拿 `code + client_id + client_secret` 调 token 端点换 `access_token`（可选 `refresh_token`）；
> 5. 客户端用 `access_token` 调资源服务器接口，拿到数据后自己签发登录态（session 或 JWT）。
> 微信扫码登录就是这套流程的定制版：scope 固定 `snsapi_login`，用 `code` 换的是微信的 `access_token + openid`。

### 8.9.3 为什么必须「code 换 token」，不直接把 token 给前端

> - `access_token` 一旦出现在浏览器 URL 或 history 里就会泄露，而**前端是不可信环境**；
> - `code` **短命（一般 5 分钟）、一次性**，即使被截获，没有 `client_secret` 也换不到 token；
> - `client_secret` 只存在服务端，保证只有合法客户端能兑换；
> - SPA / 移动端还要求 **PKCE**（`code_verifier` + `code_challenge`），防止 code 被恶意 App 拦截后兑换。

### 8.9.4 四种授权模式怎么选

| 模式 | 适用场景 | 现状 |
| --- | --- | --- |
| 授权码 code | 有后端的 Web / 开放平台 | **首选**，最安全 |
| 隐式 implicit | 纯前端老应用 | 已淘汰，token 直接暴露 |
| 密码 password | 高度信任的自有客户端 | 不推荐，等于交出密码 |
| 客户端凭证 client credentials | 服务间调用，无用户参与 | 微服务内部鉴权常用 |

### 8.9.5 OAuth2 和 OpenID Connect（OIDC）的区别

> OAuth2 只解决**授权**（能不能访问），不定义「用户身份」标准。OIDC 是在 OAuth2 上加了一层**认证**：授权码换 token 时额外返回 `id_token`（一个 JWT），里面有 `sub`、`name`、`email` 等用户信息，并提供 `userinfo` 接口。要「用第三方账号登录」就用 OIDC；只要「拿权限访问资源」用 OAuth2 即可。

### 8.9.6 JWT 的结构和原理

> 三段式，用 `.` 分隔：`Base64URL(header) . Base64URL(payload) . Base64URL(signature)`。
> - **header**：`{"alg":"HS256","typ":"JWT"}`，声明签名算法；
> - **payload**：claims，标准字段有 `sub`（主体）、`iss`（签发方）、`aud`（接收方）、`exp`（过期）、`iat`、`jti`（唯一 ID），也可放业务字段；
> - **signature**：对前两段做 HMAC-SHA256（对称，`HS256`）或 RSA/ECDSA（非对称，`RS256/ES256`）。
> 服务端验签通过就信任内容，**不需要存 session**，所以天然适合水平扩展和多服务共享登录态。
> 注意：payload 只是 Base64URL 编码，**不是加密**，谁都能解开，所以不能放敏感信息，且必须走 HTTPS。

### 8.9.7 服务端怎么校验 JWT？有哪些攻击要防

> 校验顺序：解析三段 → **限定算法白名单**（只允许约定的 HS256/RS256）→ 用密钥验签 → 校验 `exp/nbf/iat` → 校验 `iss/aud` → 业务校验（用户状态、版本号）。
> 常见攻击：
> - `alg=none` 伪造：库必须显式指定合法算法，禁止由 token 自己决定；
> - 算法混淆：把 RSA 公钥当 HMAC 密钥用（`HS256` 验 `RS256` 的 token），必须白名单；
> - 密钥泄露：密钥放配置中心/KMS，不硬编码、不进仓库；
> - 重放：token 有效期短 + `jti` 去重；
> - XSS 偷 token：存 `HttpOnly + Secure` Cookie（配合 CSRF Token），别放 localStorage。

### 8.9.8 JWT 怎么做「主动失效」/ 登出

> JWT 是无状态的，天然不能即时作废，常用组合拳：
> 1. **短有效期**：access token 5~15 分钟，配 refresh token 续期；
> 2. **黑名单**：登出/封号时把 `jti` 写入 Redis，TTL 等于剩余有效期，网关校验时查一次；
> 3. **版本号**：用户表存 `tokenVersion`，JWT 里带上，改密码或强制下线时版本 +1，旧 token 全部失效；
> 4. 敏感操作（支付、改密）二次校验或要求重新登录。

### 8.9.9 JWT 和 Session 怎么选

> - **Session**：服务端存状态，可控、可即时失效，但要共享存储（Redis），多实例要粘性/集中存储；
> - **JWT**：无状态、跨服务/跨域友好、扩展性好，但无法即时失效、体积大、续期和注销要额外设计。
> 我的选择：对外 API 和微服务间用 JWT（短 token + refresh），后台管理这类需要强控制的用 Session 或「JWT + Redis 黑名单」混合。

### 8.9.10 微信扫码登录流程（结合粤贸项目）

> 前置：微信开放平台创建「网站应用」，拿到 `AppID/AppSecret`，配置**授权回调域名**。
> 1. 前端跳转：`https://open.weixin.qq.com/connect/qrconnect?appid=APPID&redirect_uri=URLENCODE(回调地址)&response_type=code&scope=snsapi_login&state=STATE#wechat_redirect`
> 2. 用户扫码确认后，微信 302 回 `redirect_uri?code=CODE&state=STATE`；
> 3. 后端先校验 `state`（和下发时存的值比对，防 CSRF），再调 `https://api.weixin.qq.com/sns/oauth2/access_token?appid=&secret=&code=&grant_type=authorization_code`，拿到微信 `access_token`、`openid`、`unionid`；
> 4. 调 `https://api.weixin.qq.com/sns/userinfo?access_token=&openid=` 拿昵称、头像等；
> 5. 用 `unionid`（多应用统一账号）或 `openid` 查本地用户，没有就注册，最后签发自己的 token 返回前端。
> 注意点：`code` 只能用一次、5 分钟过期；`access_token` 约 2 小时、`refresh_token` 约 30 天，需要缓存刷新；`AppSecret` 只在服务端；回调域名必须和开放平台配置一致。

### 8.9.11 微信小程序登录流程

> 前端 `wx.login()` 拿临时 `code` → 后端调 `https://api.weixin.qq.com/sns/jscode2session?appid=&secret=&js_code=&grant_type=authorization_code` → 返回 `openid`、`session_key`、`unionid`。
> `session_key` 用于解密手机号等敏感数据（`wx.getPhoneNumber` 的加密串），**绝不能下发前端**；业务上同样用 `openid/unionid` 建账号，再签发自己的登录态。

### 8.9.12 state 参数是干什么的

> 防 **CSRF / 授权码注入**：发起授权前生成随机 `state` 存到 session 或短期缓存，回调时比对，不一致直接拒绝。顺带还能携带业务上下文（如登录后跳转地址、渠道标识）。

## 8.10 微信支付

### 8.10.1 微信扫码支付（Native）完整流程

> 前置：商户号 `mchid`、APIv3 密钥、商户 API 证书（`apiclient_key.pem`）、平台证书/公钥。
> 1. **下单**：服务端 `POST https://api.mch.weixin.qq.com/v3/pay/transactions/native`，body 传 `appid`、`mchid`、`description`、`out_trade_no`（商户订单号）、`notify_url`、`amount.total`（**单位分**），返回 `code_url`（约 2 小时有效）；
> 2. **展示**：前端把 `code_url` 生成二维码；
> 3. **支付**：用户扫码付款，微信向 `notify_url` 发异步通知；
> 4. **回调处理**：验签 → 解密 `resource` → 校验商户号/AppID/订单号/金额/`trade_state=SUCCESS` → 幂等更新订单 → 返回 `200 + {"code":"SUCCESS","message":"成功"}`；
> 5. **兜底**：主动查单 `GET /v3/pay/transactions/out-trade-no/{out_trade_no}?mchid=xx`，加定时对账。

### 8.10.2 支付回调怎么保证安全

> - **验签**：用微信平台证书公钥对 `Wechatpay-Timestamp + Wechatpay-Nonce + 请求体` 做 RSA-SHA256 验签，`Wechatpay-Serial` 指定证书序列号；
> - **解密**：V3 回调的 `resource` 是 AES-256-GCM 密文，用 APIv3 密钥 + `nonce` + `associated_data` 解密；
> - **业务校验**：`mchid/appid/out_trade_no` 必须和本地订单一致，**金额必须比对**（防止篡改金额），状态必须是 `SUCCESS`；
> - **时间戳**校验防重放（一般 5 分钟内）；
> - 回调地址只走 HTTPS，且要防重试风暴。

### 8.10.3 回调幂等和漏单怎么处理

> 幂等：`out_trade_no` 建唯一索引，订单状态机只允许「待支付 → 已支付」单向流转，重复回调直接返回成功；更新用 `update ... where status='待支付'` 条件更新避免并发重复。
> 漏单：微信回调可能延迟或失败，所以必须有**主动查单**（支付后前端轮询 + 后端定时查）+ **定时对账**（下载微信账单比对本地订单，差异自动补单/告警）。这两条是支付系统的标配。

### 8.10.4 V2 和 V3 的区别

| 维度 | V2 | V3 |
| --- | --- | --- |
| 数据格式 | XML | JSON |
| 签名 | MD5 / HMAC-SHA256（字段拼接） | RSA-SHA256 + 商户私钥，平台证书验签 |
| 证书 | 商户证书 | 商户证书 + 平台证书（或公钥） |
| 回调 | 明文 + 签名 | 资源 AES-256-GCM 加密 + 验签 |

> 新项目直接上 V3，安全性和规范都更好。

### 8.10.5 JSAPI / 小程序支付差异

> JSAPI（公众号 H5）：需要用户 `openid`，下单 `trade_type=JSAPI`，返回 `prepay_id`，前端用 `WeixinJSBridge.invoke('getBrandWCPayRequest', ...)` 唤起。
> 小程序：`wx.login` 拿 `openid`，下单后用 `wx.requestPayment` 唤起，参数包含 `timeStamp/nonceStr/package/signType/paySign`。
> 扫码 Native 不需要 `openid`，三者下单接口和回调逻辑基本一致，差别在唤起方式和支付参数。

### 8.10.6 退款与对账

> 退款调 `/v3/refund/domestic/refunds`，必须有唯一 `out_refund_no` 做幂等，金额不能超过可退金额；退款是异步的，要听退款回调或主动查退款单。
> 对账：每天下载交易账单，和本地订单逐笔比对，处理「本地成功微信无记录」「微信成功本地无记录」「金额不一致」，差异走人工或自动补偿。

## 8.11 加解密技术

### 8.11.1 三类算法怎么分工

> - **对称加密**（AES、ChaCha20、SM4）：加解密同一把密钥，速度快，用于**大批量数据**和会话传输；
> - **非对称加密**（RSA、ECC、SM2）：公钥/私钥分离，解决**密钥分发**和**身份认证**，速度慢，只用来加密小数据（如会话密钥）或做签名；
> - **哈希/摘要**（SHA-256、SM3）：单向不可逆，用于完整性校验、签名前置、密码存储。
> 实际系统几乎都是组合使用：非对称交换密钥 → 对称加密数据 → 哈希/HMAC 保证完整性。

### 8.11.2 AES 的模式怎么选

> AES 是分组加密（块 128 bit），密钥 128/192/256 位。
> - **ECB**：相同明文块产出相同密文，会泄露结构，**不要用**；
> - **CBC**：需要随机 IV，逐块链接，但**不防篡改**，要额外加 HMAC（Encrypt-then-MAC）；IV 不必保密但必须随机且不可复用；
> - **CTR**：把分组变流式，可并行，同样需要唯一 nonce；
> - **GCM**：AEAD，加密 + 认证一体，性能好，**推荐**；nonce 绝对不能重复，否则密钥流复用会直接泄露明文。
> 实践：AES-256-GCM，每次加密随机 nonce，密文和 nonce/tag 一起存；密钥放 KMS 或配置中心并支持轮换。

### 8.11.3 RSA 原理、填充和密钥长度

> 安全性基于**大整数分解难题**：`n = p * q`，公钥 `(n, e)`，私钥 `(n, d)`。公钥加密、私钥解密；私钥签名、公钥验签。
> - 加密填充用 **OAEP**，签名填充用 **PSS**，不要在新系统用裸 `PKCS#1 v1.5` 加密；
> - 密钥长度至少 **2048 位**（3072/4096 更稳），RSA 加密的明文长度受密钥长度限制（2048 位大约只能加密 245 字节以内），所以只加密对称密钥；
> - 同一密钥对不能既当签名密钥又当加密密钥，应按用途分离。

### 8.11.4 ECC 和国密 SM2/SM3/SM4

> **ECC** 基于椭圆曲线离散对数问题，256 位强度约等于 RSA 3072 位，密钥短、运算快，适合移动端和 TLS。`ECDH` 做密钥协商，`ECDSA` 做签名。
> 国密：**SM2**（椭圆曲线，签名/加密/密钥交换）、**SM3**（哈希，256 位）、**SM4**（分组对称，128 位）。信创、政务、金融合规场景常要求国密改造，Go 可用 `tjfoc/gmsm` 等库。

### 8.11.5 哈希、HMAC 和密码存储

> - 哈希：SHA-256 / SM3 可用于摘要和校验；**MD5/SHA1 有碰撞，不能用于安全场景**；
> - **HMAC** = 哈希 + 密钥，能防篡改和伪造，常用于 API 签名、支付回调验签、Webhook 校验；
> - **密码存储**：绝不能存明文，也不能只做一次 SHA-256（可被彩虹表/暴力破解），要用 **bcrypt / scrypt / Argon2** 这类慢哈希，自带盐、成本可调；比对用常量时间比较，防时序攻击。

### 8.11.6 数字签名和证书链

> 签名流程：对内容做哈希 → 用**私钥**对摘要签名 → 对方用**公钥**验签。保证完整性、身份认证、不可否认。
> 数字证书解决「公钥怎么可信」：CA 用自己私钥给服务器证书签名，证书里含域名、公钥、有效期；客户端用内置根 CA 公钥逐级验证证书链，再校验域名、有效期、吊销状态（CRL/OCSP）。
> HTTPS 就是「证书验证身份 + 非对称协商密钥 + 对称加密传输」的组合。

### 8.11.7 HTTPS 是怎么组合这些算法的

> 1. 客户端 ClientHello（支持的套件、随机数）；
> 2. 服务端 ServerHello + 证书链；
> 3. 客户端验证证书链，双方用 **ECDHE** 协商出预主密钥（前向保密：即使私钥泄露，历史流量也解不开）；
> 4. 用随机数派生**会话密钥**；
> 5. 之后用 **AES-GCM / ChaCha20-Poly1305** 对称加密传输，AEAD 同时保证机密性和完整性。
> 一句话：**非对称只用来协商和认证，真正传数据用对称**。

### 8.11.8 简历里「非对称加密实现登录」具体怎么做，有什么缺陷

> 做法：服务端生成 RSA 密钥对，公钥下发给前端；前端用 `JSEncrypt` 把「密码 + 时间戳 + 随机数」用公钥加密后提交；后端用私钥解密，校验时间戳/nonce 防重放，再走正常登录。
> 目的：避免密码明文出现在请求体/日志/抓包里，属于纵深防御。
> **缺陷**：HTTP 下公钥本身可被中间人替换、密文可被原样重放，所以必须配合 HTTPS、时间戳 + nonce + 一次性校验、失败限流；公钥加密不是身份认证，不能替代 TLS。
> 更稳的方案：全站 HTTPS + 服务端 bcrypt 存密码，前端加密只作为额外一层。

### 8.11.9 加解密实践的坑

> - 不要自己实现算法，用标准库/成熟库；
> - IV / nonce 不复用，随机生成；
> - 密钥不硬编码、不进代码仓库，用 KMS / 环境变量 / 配置中心，定期轮换；
> - **加密 ≠ 完整性**，需要 HMAC 或 AEAD；
> - Base64 只是编码，不是加密；
> - 日志不打明文密码、密钥、token；
> - 错误提示不暴露内部细节（如「签名错误」不要区分哪一步）；
> - 敏感字段（手机号、身份证）落库加密 + 展示脱敏。

## 8.12 Kubernetes 架构与常用命令

### 8.12.1 整体架构

> 分控制面（Control Plane）和工作节点（Node）两层：
> - 控制面：`kube-apiserver`、`etcd`、`kube-scheduler`、`kube-controller-manager`、`cloud-controller-manager`；
> - 节点：`kubelet`、`kube-proxy`、容器运行时（containerd / CRI-O）。
> 三类插件接口：**CRI**（容器运行时）、**CNI**（网络）、**CSI**（存储）。

### 8.12.2 控制面各组件职责

> - **kube-apiserver**：集群唯一入口，负责认证、鉴权、准入控制（Mutating/Validating Admission），提供 REST API，读写 etcd；
> - **etcd**：分布式 KV，集群**唯一事实源**，存所有对象和状态，通过 watch 通知变更；
> - **kube-scheduler**：为未调度的 Pod 选节点，先过滤（资源、亲和性、污点）再打分；
> - **kube-controller-manager**：跑各种控制器（Deployment、ReplicaSet、Node、Job、Endpoint 等），核心是**调谐循环 reconcile**，让实际状态收敛到期望状态；
> - **cloud-controller-manager**：对接云厂商的节点、路由、存储能力。

### 8.12.3 节点侧组件职责

> - **kubelet**：和控制面通信，管理本节点 Pod 生命周期、探针、卷挂载、上报状态，通过 CRI 调容器运行时；
> - **kube-proxy**：实现 Service 的流量转发（iptables / IPVS / nftables，部分方案用 eBPF 替代）；
> - **容器运行时**：真正拉镜像、跑容器（K8s 1.24 起移除了 dockershim，默认推荐 containerd；Docker 需通过 cri-dockerd 适配）。

### 8.12.4 一个 Pod 从 apply 到跑起来经历了什么

> 1. `kubectl apply` → apiserver 鉴权/准入 → 写入 etcd；
> 2. Deployment 控制器创建 ReplicaSet，ReplicaSet 控制器创建 Pod；
> 3. scheduler watch 到未绑定节点的 Pod → 过滤 + 打分选出节点 → 写回 `spec.nodeName`（bind）；
> 4. 目标节点 kubelet watch 到分配给自己的 Pod → 拉镜像、创建容器、配置网络/存储；
> 5. kubelet 上报状态，探针通过后 Service Endpoints 更新，流量才进来；
> 6. 控制器持续调谐：副本数不对就扩缩，Pod 挂了就重建。

### 8.12.5 常用命令清单

```bash
# 查看
kubectl get pods,deploy,svc,node -n <ns> -o wide
kubectl describe pod <pod> -n <ns>
kubectl get events -n <ns> --sort-by=.lastTimestamp

# 日志与进入容器
kubectl logs -f <pod> -c <container>
kubectl logs <pod> --previous          # 看崩溃前的日志
kubectl exec -it <pod> -- sh

# 发布与回滚
kubectl apply -f app.yaml
kubectl delete -f app.yaml
kubectl rollout status deployment/<name>
kubectl rollout undo deployment/<name>
kubectl rollout restart deployment/<name>
kubectl scale deployment/<name> --replicas=3

# 调试与网络
kubectl port-forward svc/<name> 8080:80
kubectl create configmap <name> --from-file=...

# 节点维护

kubectl auth can-i <verb> <resource>
```

### 8.12.6 排障常用命令与典型状态

> - **Pending**：`describe pod` 看 Events，常见是资源不足、亲和性/污点不满足、PVC 没绑定、镜像拉不下来；
> - **CrashLoopBackOff**：`logs --previous` 看上次退出原因，常见是配置错、依赖连不上、启动即 panic；
> - **ImagePullBackOff**：镜像名/tag 错、私有仓库没配 `imagePullSecrets`、网络不通；
> - **OOMKilled**：超内存 `limits` 被 kill，看 `describe pod` 的 Last State 和监控；
> - **节点 NotReady**：`describe node` + 登节点看 kubelet/容器运行时日志、磁盘是否满、证书是否过期；
> - **Service 访问不通**：看 Endpoints 是否有后端、selector 是否匹配、`kube-proxy` 是否正常、NetworkPolicy。

### 8.12.7 client-go 怎么和集群交互（结合算力调度）

> 用 `clientset` 创建/查询/删除 Job、Deployment、Pod，读事件和状态；长驻服务用 **Informer**（List 全量 + Watch 增量）在本地维护缓存，业务读缓存而不是直连 apiserver，配合 workqueue 处理事件，避免把 apiserver 打爆。
> 任务下发用固定名称 + label 带任务 ID 保证幂等；以 K8s 为事实源，定时 reconcile 修正本地状态。

## 8.13 Prometheus 查询语句

### 8.13.1 四种指标类型

> - **Counter**：只增不减（请求数、字节数），用 `rate()/increase()`；
> - **Gauge**：可增可减（温度、内存、GPU 利用率），直接取值或用 `delta()/avg_over_time()`；
> - **Histogram**：分桶统计（`_bucket`、`_sum`、`_count`），用 `histogram_quantile()` 算分位数；
> - **Summary**：客户端算好分位数，**不能跨实例聚合**，多实例场景不如 Histogram。

### 8.13.2 常用 PromQL 函数

> - `rate(m[5m])`：每秒平均速率，适合告警；`irate(m[5m])`：最后两点瞬时速率，更敏感但抖动大；
> - `increase(m[1h])`：区间增量；
> - `sum/avg/max/min/count by (label)`：聚合，`by` 保留标签，`without` 排除标签；
> - `topk(5, ...)`：取 TopN；
> - `avg_over_time / max_over_time`：区间内平均/最大；
> - `histogram_quantile(0.99, sum by (le) (rate(..._bucket[5m])))`：P99；
> - `predict_linear(metric[1h], 4*3600)`：线性预测未来值；
> - `absent(metric)`：缺失检测；`offset 1d`：同比；`@`：固定时间点。

### 8.13.3 实战查询（GPU / 节点 / 接口）

```promql
# 各节点 GPU 平均利用率
avg by (node) (DCGM_FI_DEV_GPU_UTIL)

# 单卡显存使用率
100 * DCGM_FI_DEV_FB_USED / (DCGM_FI_DEV_FB_USED + DCGM_FI_DEV_FB_FREE)

# 各节点 GPU 总功耗（瓦）
sum by (node) (DCGM_FI_DEV_POWER_USAGE)

# 节点 CPU 使用率
100 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100

# 节点内存使用率
100 * (1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)

# 磁盘使用率（排除临时文件系统）
100 * (node_filesystem_size_bytes{fstype!~"tmpfs|overlay"} - node_filesystem_free_bytes{fstype!~"tmpfs|overlay"})
    / node_filesystem_size_bytes{fstype!~"tmpfs|overlay"}

# 接口 QPS 与 P99 延迟
sum by (path) (rate(http_requests_total[5m]))
histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))

# 5xx 错误率
sum(rate(http_requests_total{code=~"5.."}[5m])) / sum(rate(http_requests_total[5m]))

# 实例探活
up == 0
```

### 8.13.4 告警和预测

> - 记录规则（recording rule）：把高频复杂查询预计算成新指标，降低查询成本；
> - 告警规则：`expr` + `for: 5m` 防抖动 + `labels/annotations`；
> - 磁盘预测：`predict_linear(node_filesystem_free_bytes[1h], 4*3600) < 0` 表示 4 小时内会写满；
> - Alertmanager 负责分组、抑制、静默和路由。

### 8.13.5 通过 HTTP API 查询（项目里同步资源）

> - 瞬时查询：`GET /api/v1/query?query=<urlencoded>&time=<unix>`
> - 区间查询：`GET /api/v1/query_range?query=&start=&end=&step=`
> - 元数据：`/api/v1/labels`、`/api/v1/series`、`/api/v1/targets`
> 算力调度里我定时调 instant query，按 node/卡型聚合后落库做资源快照，页面展示和调度决策结合快照 + 实时查询，避免每次页面都打 Prometheus。

## 8.14 爬虫策略、反爬与 HTTPS 处理

### 8.14.1 爬虫整体策略

> 按链路拆：**目标分析 → 调度 → 抓取 → 去重 → 限速 → 解析 → 清洗入库 → 监控**。
> - 目标分析：静态页面直接解析 DOM；SPA 优先找 XHR 接口；有签名/加密才考虑逆向或浏览器；
> - 调度：crontab 定时 + 队列分发，按站点/类型隔离，支持优先级和断点续爬；
> - 抓取：连接池复用、超时控制、重试退避；
> - 去重：URL 规范化 + Redis Set/布隆过滤器，内容 hash 二次去重；
> - 限速：按域名独立限流，控制并发，避免把对方打挂；
> - 入库：结构化清洗后写库，原始页面可落对象存储备查；
> - 监控：成功率、耗时、队列积压、被封比例。

### 8.14.2 项目架构回顾

> Beego 服务 + crontab 定时触发 → 投递 RabbitMQ（**direct 交换机**，每类爬虫一个 routing key + 独立队列）→ 消费者独立消费、独立扩容 → 解析清洗入库 → 供其他系统使用。
> 好处：抓取和解析解耦，单个站点失败不影响其他站点；失败进死信队列重试；按队列长度单独扩容。

### 8.14.3 去重、增量、限速

> - 去重：URL 统一小写、去掉 `#fragment`、参数排序后再 hash；Redis Set 存已抓 URL，量大用布隆过滤器（有假阳性，需配合 DB 兜底）；
> - 增量：列表页按更新时间/ID 游标只拉新增；详情页对比 `update_time` 或内容 hash，没变就跳过；
> - 限速：每域名令牌桶/固定间隔，分布式场景用 Redis 计数；失败率升高时自动降速（自适应）。

### 8.14.4 常见反爬手段与应对

| 反爬手段 | 表现 | 应对 |
| --- | --- | --- |
| UA / Referer / Header 校验 | 直接 403 | 维护真实浏览器 Header 池，按站点配置 |
| IP 频率限制、封禁 | 429 / 验证码 / 空数据 | 代理池（质量检测、失败剔除）、降频、多出口 |
| 登录态 / Cookie 校验 | 未登录返回空 | Cookie 池、账号池、定期刷新会话 |
| 验证码（图形/滑块） | 拦截页 | 控制频率避免触发；OCR/打码平台；滑块用浏览器自动化 |
| JS 参数签名 / 加密 | 参数对不上就拒绝 | 逆向 JS（扣代码/补环境），或用 headless 浏览器直接执行 |
| 字体反爬 | 页面数字是乱码 | 下载字体文件，建立字形到真实字符的映射 |
| 动态渲染 | HTML 里没有数据 | 找底层接口，或 Playwright/Chrome DevTools Protocol 渲染 |
| TLS 指纹（JA3/JA4） | 请求直接被拒 | uTLS、curl_cffi、真实浏览器指纹 |
| 蜜罐 / 假数据 | 数据异常 | 数据合理性校验，不采信异常链接 |

> 原则：优先用官方 API / RSS；能用接口就不解析页面；能降频解决就不硬刚验证码。

### 8.14.5 法律与合规

> 遵守 `robots.txt` 和网站协议；控制频率不影响对方正常服务；不抓取个人信息、隐私、付费内容；不绕过登录/付费墙/技术保护措施；数据使用注意版权，符合《网络安全法》《数据安全法》《个人信息保护法》。面试时主动提合规，是加分项。

### 8.14.6 HTTPS 链接处理（Go）

> Go 的 `net/http` 默认就会做 TLS 握手和证书校验，正常 HTTPS 直接请求即可。特殊场景：
> - **自签证书/测试环境**：`tls.Config{InsecureSkipVerify: true}`，仅限测试，生产禁止；
> - **指定 CA**：`RootCAs` 加载 PEM；**双向认证 mTLS**：`Certificates` 加载客户端证书；
> - **连接池**：自定义 `http.Transport`，设置 `MaxIdleConns`、`MaxIdleConnsPerHost`、`IdleConnTimeout`，并设置 `DialContext`/`ResponseHeaderTimeout` 超时；
> - **重定向**：默认跟随会丢 Cookie/丢 Header，需要 `CheckRedirect` 手动处理或用 `cookiejar`；
> - **相对链接**：`url.Parse` + `ResolveReference` 拼成绝对地址。

```go
tr := &http.Transport{
    MaxIdleConns:        100,
    MaxIdleConnsPerHost: 10,
    IdleConnTimeout:     90 * time.Second,
    TLSClientConfig:     &tls.Config{MinVersion: tls.VersionTLS12},
}
client := &http.Client{
    Transport: tr,
    Timeout:   15 * time.Second,
    CheckRedirect: func(req *http.Request, via []*http.Request) error {
        if len(via) >= 5 {
            return errors.New("too many redirects")
        }
        return nil
    },
}
```

### 8.14.7 抓包调试与 TLS 指纹

> 调试：把 `Transport.Proxy` 指向本地 mitmproxy/Charles，并在客户端信任其 CA 证书（只在自己环境做）。
> 有些站点会校验 **TLS 指纹**（JA3/JA4）或 HTTP/2 指纹，标准库请求会被识别为非浏览器。应对：用 uTLS 定制指纹、`curl_cffi`，或直接用真实浏览器（Playwright）。

### 8.14.8 爬虫稳定性设计

> - 超时 + 重试 + 指数退避 + 最大次数，失败进死信队列；
> - 按域名熔断：连续失败暂停该域名，避免持续被封；
> - 任务幂等：同一 URL 重复消费不重复入库（唯一索引/去重表）；
> - 数据校验：字段完整性、数量突变告警（防解析规则失效或拿到假数据）；
> - 可观测：抓取量、成功率、耗时、队列积压、被封率做成监控面板。

## 8.15 Python（AI 项目相关）

### 8.15.1 Python 和 Go 的区别，你怎么选

> - **类型**：Python 动态类型、开发快，适合 AI/数据处理（生态几乎所有库都是 Python）；Go 静态强类型、编译期检查，适合高并发后端和基础设施。
> - **并发**：Go 是 goroutine + GMP，轻量协程，天然多核并行；Python 受 GIL 限制，CPU 密集只能多进程，IO 密集靠 asyncio 协程。
> - **性能**：Go 编译执行，内存占用小、启动快；Python 解释执行，慢一到两个数量级，但 AI 场景瓶颈在模型推理，不在 Python 本身。
> - **我的用法**：业务服务和云原生组件用 Go；RAG 的文档解析、embedding、LangChain 编排用 Python + FastAPI，各自用擅长的部分，通过 HTTP/gRPC 互通。

### 8.15.2 GIL 是什么，有什么影响

> GIL（全局解释器锁）保证同一时刻只有一个线程执行 Python 字节码，所以**多线程不能并行跑 CPU 密集任务**，但 IO 等待时会释放 GIL。
> 结论：
> - IO 密集（HTTP、DB、读文件）→ 多线程或 asyncio 有效；
> - CPU 密集（解析、embedding 前的预处理、大计算）→ 用**多进程**（`multiprocessing` / `ProcessPoolExecutor`）或把活交给 C 扩展（numpy、FAISS 内部会释放 GIL）；
> - 3.13 起有实验性的 free-threaded 构建，但生产上主流仍按 GIL 模型设计。

### 8.15.3 协程 / asyncio 的原理

> 事件循环（event loop）单线程调度所有任务：遇到 `await` 时把控制权交回循环，注册好 IO 回调，等数据就绪再恢复执行，所以一个线程能扛大量并发连接。
> 关键点：
> - 只有 `async def` 里的 `await` 才会让出；**同步阻塞代码（`requests`、`time.sleep`、读大文件）会卡死整个循环**，要用 `httpx.AsyncClient`、`asyncio.sleep`，或 `run_in_executor` 丢到线程池；
> - CPU 密集任务用 `ProcessPoolExecutor`，别放事件循环里；
> - 协程不是并行，是并发，适合 IO 密集。

### 8.15.4 FastAPI 为什么快 / 有什么特点

> - 基于 **ASGI**（uvicorn 跑），原生支持 async，IO 密集场景并发高；
> - 用 **Pydantic** 做请求/响应模型校验和序列化，类型注解即文档；
> - 自动生成 **OpenAPI/Swagger** 文档；
> - **依赖注入**（`Depends`）：鉴权、DB session、配置注入很干净；
> - 性能上比 Flask/Django 快，但比 Go 差，所以它做 AI 服务的接入层，重活交给模型和向量库。
> 项目里 FastAPI 负责文档上传、解析任务提交、检索问答和流式输出（SSE / StreamingResponse）。

### 8.15.5 可变默认参数、深浅拷贝这类基础题

> - `def f(x, items=[])`：默认参数**只在函数定义时求值一次**，多次调用共享同一个 list，正确写法是 `items=None` 再在函数内初始化。
> - `copy.copy` 浅拷贝：只复制最外层，嵌套对象还是引用；`copy.deepcopy` 递归复制，但慢，且要处理循环引用。
> - `is` 比身份（内存地址），`==` 比值；小整数和短字符串有缓存，所以 `is` 有时「看起来对」，但不要依赖。
> - 闭包与 `late binding`：`for` 里创建 lambda 引用循环变量，最后都拿到同一个值，用默认参数或 `functools.partial` 固定。

### 8.15.6 装饰器原理

> 装饰器本质是**接受函数、返回新函数的高阶函数**，`@decorator` 等价于 `func = decorator(func)`。用 `functools.wraps` 保留原函数名和文档，否则日志和调试信息会乱。
> 项目里用它做：接口耗时统计、异常捕获与统一返回、重试（`tenacity`）、缓存（`lru_cache`）、鉴权。

### 8.15.7 生成器、迭代器、内存

> - 迭代器实现 `__iter__` + `__next__`；生成器用 `yield` 自动实现迭代器，**惰性求值**，一次只产出一个值。
> - 大文件/大文档解析必须用生成器或流式读，不能 `read()` 全量进内存；`yield` 还能把「读取 → 分块 → 向量化」做成流水线，降低峰值内存。
> - 列表推导式生成完整列表占内存，数据量大时用生成器表达式 `(x for x in ...)`。

### 8.15.8 内存管理与垃圾回收

> 以**引用计数**为主，计数归零立即释放；引用计数解决不了**循环引用**，所以配**标记-清除**和**分代回收**（0/1/2 代，越老越少扫描）。
> 实践：大对象用完及时 `del` 并解除引用；避免全局缓存无限增长（用 `functools.lru_cache(maxsize=)` 或定期清理）；内存问题用 `tracemalloc`、`objgraph`、`memory_profiler` 定位。

### 8.15.9 项目相关：文档解析和 embedding 怎么优化

> - **多格式解析**：MarkItDown 统一转 Markdown，按文件类型分派；扫描件走 OCR，损坏/加密文件捕获异常跳过并记录，单个文件失败不影响整批。
> - **大文件**：流式读取 + 分块处理，避免一次性加载；解析任务丢进队列异步跑，前端轮询或 SSE 拿进度。
> - **embedding**：**批量**调用（batch size 按显存/内存调），比逐条快很多；结果缓存（内容 hash → 向量），重复文档不重复算；GPU 推理时把 batch 拉满，CPU 环境控制并发。
> - **并发**：embedding 是 CPU/GPU 密集，用进程池或交给推理服务；文档下载、OCR 这类 IO 用线程池/协程。

### 8.15.10 项目相关：LangChain 链路怎么串的

> 文档上传 → MarkItDown 解析成 Markdown → 结构感知分块 → `bge-large-zh-v1.5` 生成向量 → 写入 FAISS 索引（带 metadata：文档 ID、标题路径、页码）。
> 问答时：问题向量化 → FAISS Top-K 召回（可叠加关键词检索做混合）→ 拼 Prompt（系统提示 + 检索片段 + 历史对话）→ 调 LLM → 流式返回并附引用来源。
> LangChain 在里面负责 `DocumentLoader / TextSplitter / Embeddings / VectorStore / Retriever / PromptTemplate / LLM` 这些组件的编排，好处是换模型、换向量库只改配置；坑是版本迭代快、抽象层厚，出问题要看源码定位，关键路径我会直接用 SDK 调，避免被框架黑盒卡住。

### 8.15.11 Python 服务怎么部署和排障

> - 部署：`uvicorn`/`gunicorn` 多 worker，Docker 镜像，K8s 探针；依赖用 `requirements.txt` 或 `poetry` 锁定版本，**AI 库版本必须锁死**，否则线上行为会变。
> - 排障：`logging` 结构化日志 + traceId；CPU/内存看 `top`、`py-spy` 抓栈（不用改代码就能看卡在哪）；内存用 `tracemalloc`；接口慢先看是不是同步阻塞卡了事件循环、下游 LLM/向量库超时。
> - 超时与重试：LLM 调用必须设超时 + 重试 + 降级（返回兜底话术），否则一个慢请求会把 worker 占满。
